## 2. 总体架构

```
┌─────────────────────────────────────────────────────┐
│  浏览器                                               │
│   住客端页面（P-C1~C8）   前台管理端页面（P-A1~A5）      │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP / JSON（/api/**）
┌──────────────────────▼──────────────────────────────┐
│  Spring Boot 单应用（单 jar）                          │
│   ├─ 静态托管前端构建产物（决策 7）                     │
│   └─ 业务模块：auth / room / inventory / order        │
└──────────────────────┬──────────────────────────────┘
                       │ JDBC
┌──────────────────────▼──────────────────────────────┐
│  MySQL 8（docker-compose 容器）                        │
└─────────────────────────────────────────────────────┘
```

- **一个工程、两端页面**：前端是单页应用，住客端与前台管理端是同一份构建产物里的两组路由（按路径前缀区分，见 §3.3），不拆成两个前端工程。
- **dev 模式**：`vite dev`（默认 5173 端口）通过 proxy 把 `/api` 转发到 `localhost:8080`，前后端分开热更新开发。
- **交付模式**：`vite build` 产物拷入后端 `static/` 目录，单 jar 启动后 `http://localhost:8080` 即可访问完整系统。**前端路由使用 hash 模式**（`/#/room/1`），静态托管下刷新任意路径都落在 index.html 上，无需后端 fallback 配置。

### 2.1 一键启动流程（start.sh 负责完整构建并启动）

1. `npm run build` 构建前端（`hotel-web/`）；
2. 前端产物复制到 `hotel-server/src/main/resources/static/`；
3. `mvn package` 打出单 jar；
4. `docker compose up -d` 启动 MySQL 容器；
5. 轮询等待 MySQL 就绪（`mysqladmin ping` 或等价探测）；
6. `java -jar hotel-server.jar` 启动应用；`schema.sql` + `data.sql` 完成建表与预置数据（房型 3~4 种、每房型若干房间、admin 账号，满足 AC-20），脚本幂等可重复启动（见 §4.2）；启动后由 `InventoryPreCreator` 幂等预创建未来 730 天的库存行（决策 13）。

> 前置条件：演示机器需预装 JDK 17、Maven、Node.js、Docker，start.sh 逐项检测并给出友好报错。admin 预置账号的明文密码写入 README 与 `data.sql` 注释，供演示登录使用。

**分层职责与调用约束**：

- `controller`：参数格式校验（`@Validated`）、鉴权注解/拦截器配合、调用模块接口、组装响应。不写业务逻辑。
- `service`：模块接口所在地，承载全部业务规则与事务边界（含业务规则校验，如预订日期规则 BR-01）。controller 只依赖本模块 service；跨模块调用只允许 `order → inventory`、`order → room`（见 §3.4 依赖图）。
- `mapper`：MyBatis-Plus 接口，仅被本模块 service 使用，不跨模块暴露。
- `entity / dto`：entity 对应表结构；dto 为接口出入参，controller 不直接向外暴露 entity。

### 3.4 后端模块划分（深模块设计）

模块划分遵循 deep module 原则：**小接口、深实现**。调用方和测试只跨越模块接口（seam），接口背后的复杂机制不外泄。

| 模块 | 模块接口（对外可见的全部） | 接口背后隐藏的复杂度 |
| --- | --- | --- |
| **auth** | `register` / `login` / `logout` / `resolveUser(token)` | BCrypt 校验、token 生成与过期、角色判定、住客与 admin 单表共存 |
| **room** | 房型/房间查询、房型/房间维护、 `listAssignableRooms(typeId)` | 房间状态不入库、由在住订单推导；维护时"房间数 ≥ 有效订单数"校验（UC-09）；房间数变更同步未来库存行总数 |
| **inventory** | `queryAvailability(typeId, checkin, checkout)` / `tryOccupy(...)` / `release(...)` | 逐日库存行的预创建与懒建兜底、并发原子占用、剩余量取逐日最小值（BR-02）、取消/退房释放 |
| **order** | 创建/取消/我的订单/详情（住客侧）；按号或手机号查询/办理入住/办理退房（前台侧） | 订单号生成、金额固化、状态机校验、入住窗口校验、身份证登记、房间分配 |

**依赖方向**（单向，无环）：

```
controller 层  →  本模块 service
order service  →  inventory service（占/释库存）
order service  →  room service（查可分配房间）
auth           →  被拦截器依赖（resolveUser），不依赖其他业务模块
inventory      →  不依赖 order（释放库存由 order 调 release 触发）
```

**模块深度说明**：

- **inventory 是最深的模块**：接口只有 3 个方法，但防超卖这一全系统唯一的并发硬规则（BR-02 / AC-08）完全封闭在内。订单模块不需要知道"逐日库存表"的存在，只面对"试着占用，占不到就失败"的语义。seam 在 `InventoryService` 接口，MyBatis-Plus mapper 是该 seam 的 adapter；并发测试直接对着这个接口做。
- **order 模块的状态机**：状态流转表（PRD §6.2）收敛为 `OrderService` 内部的转移校验，对外只有 `cancel / checkIn / checkOut` 三个动作方法，非法流转一律在模块内拒绝——controller 不出现状态判断分支。
- **不做假 seam**：四个模块各只有一个实现、没有第二个 adapter，因此模块间用普通类注入而非"接口 + Impl + 配置切换"的形式化抽象。`AuthService` 等定义为类即接口，不为抽象而抽象。
- **删除测试**：若删除 inventory 模块，逐日计算、并发占用、释放逻辑会散落到 order 和 room 的每个调用点——它确实在挣钱，不是透传层。

### 3.5 前后端交互方式

- **协议**：REST + JSON，全部业务接口挂在 `/api` 前缀下；前端构建产物由后端静态托管，同源部署无 CORS 问题（CORS 仅在 dev 模式放开）。
- **认证传递**：登录成功后后端返回 token，前端存入 `localStorage`，之后每次请求由 axios 拦截器放入请求头 `X-Token: <uuid>`；后端 `AuthInterceptor` 解析 token、注入当前用户，并按路径规则做角色鉴权（`/api/admin/**` 仅 admin 可用）。
- **统一响应体**：所有接口返回 `Result<T>`：

  ```json
  { "code": 0, "message": "ok", "data": { } }
  ```

  `code = 0` 成功；非 0 为业务错误码（错误码枚举集中在 `common/api`，如 `1001` 已订满、`1002` 手机号已注册、`1003` 不满足入住条件）；完整错误码表在编码阶段补全，前端一律以 `message` 为展示准绳，不对 code 做分支逻辑（预订失败跳结果页等少数流程除外）。HTTP 状态码仅用 200/401/403/500 表达传输层语义。
- **错误呈现**：`request.js` 统一拦截非 0 code，用 Element Plus `ElMessage` 弹出后端 `message`——后端业务异常的 message 直接采用原型文档中的提示文案（如"该房型所选日期已订满"），保证演示讲解与原型一致；页面可自行捕获做定制展示（如预订失败跳 P-C6）。
- **日期与金额的接口格式**：日期用 `yyyy-MM-dd` 字符串（LocalDate）。金额在前后端接口间一律以**"分"为单位的整数**传输（如 288.50 元 ↔ `28850`），避免 JS 浮点数精度问题；后端内部计算仍用 BigDecimal（单位元，DB 存 DECIMAL(10,2)），元 ↔ 分的换算收敛在 DTO 序列化层一处完成；前端展示时 `分 ÷ 100` 格式化即可。

## 4. 数据库设计

字符集 utf8mb4，InnoDB。表名避开关键字（订单表用 `hotel_order`）。

### 4.1 表清单

| 表 | 用途 | 关键字段与约束 |
| --- | --- | --- |
| `user` | 住客与 admin 账号（决策 11） | `login_name` 唯一（住客=手机号，admin="admin"）、`password_hash`（BCrypt）、`role`（GUEST/ADMIN）、`created_at` |
| `auth_token` | 登录 token（决策 6、12） | `token`（UUID）主键、`user_id`、`expires_at`、`created_at` |
| `room_type` | 房型 | `name`、`price` DECIMAL(10,2)、`description`、`created_at`；不提供删除（PRD 无下线需求） |
| `room` | 物理房间 | `room_no` 唯一、`room_type_id`、`created_at`；**无状态字段**，"空闲/入住中"由在住订单推导 |
| `hotel_order` | 订单 | `order_no` 唯一、`user_id`（下单账号）、`guest_name` + `guest_phone`（住客信息，支持代订 BR-01）、`room_type_id`、`room_id`（入住前为 NULL）、`id_card`（入住前为 NULL）、`checkin_date`、`checkout_date`、`nights`、`amount` DECIMAL(10,2)（下单时固化 BR-03）、`status` 枚举字符串、`created_at`（下单时间，P-C8/P-A2 展示用）、`updated_at`；生成列 `active_room_id = IF(status='CHECKED_IN', room_id, NULL)` 加唯一索引，DB 级保证同一房间最多一笔已入住订单（BR-05，MySQL 唯一索引允许多个 NULL） |
| `daily_inventory` | 逐日库存（决策 5） | `room_type_id` + `stay_date` 唯一索引、`total_count`、`occupied_count` |
| `order_seq` | 订单号每日序号（决策 8） | `seq_date` 主键、`current_value` |

### 4.2 关键设计说明

- **库存与房间数的一致性**：`daily_inventory.total_count` 是该房型在 `stay_date` 当日的房间数快照。库存行在启动时与房型/房间变更时预创建（决策 13）：`INSERT IGNORE` 批量创建 `[今天, 今天+730 天)` 的行，`total_count` 取当前房间数；UC-09 维护房间（增/减/改挂）时，先校验"新房间数 ≥ 当前有效订单数"，再把 `stay_date ≥ 今天` 的库存行 `total_count` 同步为新值（不存在的行随预创建一并补上）。历史日期行不改。**将房间改挂其他房型时，源房型与目标房型都要做有效订单校验与库存行同步。**
- **房间状态推导**：某房型当前空闲房间 = 该房型全部房间 − 被状态为"已入住"订单占用的房间。满足 BR-05"同一房间同一时间只分配给一笔已入住订单"，由"分配时房间行锁 + 生成列唯一索引"双重保证（见 §4.1、§5.3），也让 UC-09 的房间维护不受"房间状态"字段拖累。
- **订单状态**：Java 枚举 `CONFIRMED / CHECKED_IN / COMPLETED / CANCELLED`，DB 存字符串，便于 SQL 直读与演示讲解。
- **初始化脚本幂等**：`schema.sql` 一律 `CREATE TABLE IF NOT EXISTS`，`data.sql` 用 `INSERT IGNORE`（或等价写法），应用重复启动不报错、预置数据不重复插入。

## 5. 核心机制设计

### 5.1 防超卖（BR-02 / AC-08）

创建订单先由 service 层做**业务规则校验**（BR-01：入住日期 ≥ 当天、离店日期 > 入住日期、住客姓名非空、手机号格式合法），校验不通过直接拒绝，不进入库存占用。

库存行**预创建**（决策 13）：应用启动时与房型/房间变更时，按 `INSERT IGNORE` 批量创建 `[今天, 今天+730 天)` 的逐日库存行（`total_count` 取当前房间数）。预创建保证下单热路径上库存行**总是存在**——这是并发安全的前提，原因见本节末尾。

校验通过后在**一个事务**内，对日期区间 `[checkin, checkout)` 的每一天**按日期升序**执行（固定加锁顺序，降低并发事务死锁概率）：

1. 原子条件更新：
   `UPDATE daily_inventory SET occupied_count = occupied_count + 1 WHERE room_type_id = ? AND stay_date = ? AND occupied_count < total_count`
2. 影响行数 = 1 → 该日占用成功；= 0 → 行存在但已订满，或超出预创建窗口（行不存在）。先用无锁一致性读区分：行不存在则经**独立小事务**懒建该行（`INSERT IGNORE`，立即提交），随后重试一次条件更新。
3. 重试后仍为 0 → 当日已订满，**抛业务异常、整单回滚**（已占用的日期行随事务一并回滚），返回"该房型所选日期已订满"。
4. 全部日期占用成功 → 插入订单，提交事务。

并发正确性由两点保证：`occupied_count < total_count` 的条件更新在 MySQL 行锁下是原子的（不超卖）；`(room_type_id, stay_date)` 唯一索引防止库存行重复。

**为什么不能在下单事务内建行**（v1.2 实测结论）：下单事务里 INSERT 库存行有两类并发死锁——① REPEATABLE READ 下对不存在的行做加锁 UPDATE 会产生间隙锁，并发 INSERT 同一间隙互相等待成环；② INSERT 撞唯一索引后 InnoDB 为重复键检查持有该记录的 S 锁直到事务结束，并发事务再请求 X 锁形成 S→X 升级死锁（READ COMMITTED 下同样存在）。预创建把"行存在"变成数据不变式后，占用路径只剩对已存在行的条件更新（纯记录锁），配合日期升序的固定加锁顺序，无死锁面；懒建兜底走独立小事务，同样不把 INSERT 引入下单事务。

查询剩余量（无需事务）：区间内每日 `total_count − occupied_count` 的最小值；无库存行的日期按 `total_count = 当前房间数, occupied = 0` 计。

取消（已确认 → 已取消）与提前退房（已入住 → 已完成）时，对订单区间每日执行 `occupied_count − 1`（带 `occupied_count > 0` 保护，同样按日期升序）。退房时剩余晚数立即可再售，正好由"逐日释放"天然满足（BR-07）。

### 5.2 订单号生成（BR-08 / 决策 8）

`OrderNoGenerator`（order 模块内部实现，不对外）：

1. 事务内对 `order_seq` 当日行执行 `UPDATE ... SET current_value = current_value + 1 WHERE seq_date = 今天`，影响 0 行则 INSERT 初始行（撞主键则重试 UPDATE）；
2. 格式化 `HR + yyyyMMdd + '-' + 序号补零4位`，如 `HR20261003-0001`；
3. 与订单插入同一事务，序号不回滚复用（允许跳号，唯一性优先）。

### 5.3 状态流转与条件更新

所有状态变更用**带源状态条件的 UPDATE** 实现，杜绝"先查后改"的并发缝隙：

- 取消：`UPDATE hotel_order SET status='CANCELLED' WHERE order_no=? AND status='CONFIRMED' AND user_id=?`，影响 0 行 → "订单状态已变更，请刷新查看"。
- 办理入住（一个事务内，按序执行）：
  1. BR-06 四项校验：订单状态 = 已确认、入住窗口 `入住日 ≤ 今天 < 离店日`、身份证 18 位格式、该房型有空闲房间；
  2. 对选中的房间行加行锁 `SELECT * FROM room WHERE id=? FOR UPDATE`——这是防止"同一房间被两笔订单并发分配"的关键：并发事务在此串行化；
  3. 锁内复查该房间无在住订单（`SELECT COUNT(*) FROM hotel_order WHERE room_id=? AND status='CHECKED_IN'`，> 0 则抛业务异常回滚，提示"房间刚被分配，请刷新重选"）；
  4. `UPDATE hotel_order SET status='CHECKED_IN', room_id=?, id_card=? WHERE id=? AND status='CONFIRMED'`，影响 0 行 → 订单状态已变更，回滚。

  兜底：`hotel_order` 上的生成列唯一索引（§4.1）把"同一房间最多一笔已入住订单"固化为数据库约束，代码路径即使失守也写不进去。
- 办理退房：`UPDATE ... SET status='COMPLETED' WHERE order_no=? AND status='CHECKED_IN'`，随后释放库存（§5.1）。

终态（已完成/已取消）无任何出口流转，与 PRD §6.2 一致。

### 5.4 认证与鉴权

- 注册：校验手机号格式与唯一性，BCrypt 加密入库。
- 登录：按 `login_name` 查用户、BCrypt 比对，成功则生成 UUID token 写入 `auth_token`（含过期时间，如 7 天），返回 token 与角色。
- `AuthInterceptor`：从 `X-Token` 解析用户并放入请求上下文；未登录访问需登录接口 → 401；住客访问 `/api/admin/**` → 403（AC-04）。
- 住客"我的订单"一律以 token 中的 `user_id` 过滤，不接受前端传 userId（AC-03）。
