## 1. 项目目标与范围

### 1.1 项目目标

做一个带前后端的酒店业务系统，覆盖完整业务主链路：

**浏览房型 → 创建预订 → 查询订单 → 前台办理入住 → 退房完成**

系统需保证核心业务规则正确（防超卖、状态流转、入住校验），可支撑面试现场全流程演示。

### 1.2 本期范围（做什么）

- 住客侧：注册/登录、浏览房型、按日期查询可订状态、创建预订、查询本人订单、取消订单
- 前台侧：登录、查询全部订单、办理入住（含房间分配、身份证登记）、办理退房、房型与房间的简单维护
- 订单金额计算与展示（到店支付，不做在线支付）

### 1.3 本期不做（明确排除）

| 排除项 | 说明 |
| --- | --- |
| 在线支付 | 订单仅记录金额，标注"到店支付"；预留金额字段便于后续扩展 |
| 订单改期 | 改期通过"取消后重新预订"实现 |
| 一单多间/多房型 | 一个订单 = 一个房型 × 一间房 × 连续多晚；订多间需下多个订单 |
| 浮动房价 | 不做周末价/节假日价，每房型一个固定单价 |
| 会员/积分/优惠券/发票/评价 | 均不纳入 |
| 短信/邮件通知 | 不纳入 |
| 权限分级 | 前台只有一个预置 admin 角色，不做店长、财务等分级 |
| 房间维修/停用状态 | 房间仅区分"空闲/入住中"，不做维修/停用管理；库存始终等于物理房间总数 |
| 埋点、运营报表、监控告警 | 演示项目省略，见 8.3 说明 |

## 2. 用户与角色

### 2.1 角色定义

| 角色 | 来源 | 说明 |
| --- | --- | --- |
| 游客（未登录） | 无需账号 | 仅可浏览房型信息；进行预订时引导注册/登录 |
| 住客 | 自助注册 | 预订、查询/取消本人订单 |
| 前台 | 系统预置 admin 账号 | 查询全部订单、办理入住/退房、维护房型与房间；不提供前台账号注册入口 |

| 查询/取消订单 | ✗ | 仅本人订单 | 全部订单（仅查询，不代取消） |
| 办理入住/退房 | ✗ | ✗ | ✓ |
| 房型与房间维护 | ✗ | ✗ | ✓ |

## 3. 核心用例

### UC-01 住客注册与登录

- **参与者**：住客
- **主流程**：住客填写手机号、密码完成注册 → 使用手机号+密码登录 → 进入住客首页
- **异常**：手机号已注册则提示；密码错误则提示

### UC-02 浏览房型与查询可订状态

- **参与者**：游客 / 住客（无需登录）
- **主流程**：进入房型列表页 → 查看房型名称、单价、介绍 → 选择入住日期与离店日期 → 系统展示各房型在该日期区间的可订状态与剩余数量
- **异常**：日期区间无剩余数量的房型展示为"已订满"

### UC-03 创建预订

- **参与者**：住客（已登录）
- **前置条件**：所选房型在所选日期区间有可订数量
- **主流程**：住客选择房型与日期区间 → 填写住客姓名、手机号 → 确认订单金额（单价 × 晚数）→ 提交 → 系统生成订单（订单号含 HR+日期），订单状态为"已确认"
- **异常**：提交瞬间库存被占满（并发）→ 预订失败并提示"该房型所选日期已订满"

### UC-04 查询我的订单

- **参与者**：住客
- **主流程**：进入"我的订单" → 列表展示本人全部订单（订单号、房型、日期、金额、状态）→ 可查看订单详情

### UC-05 取消订单

- **参与者**：住客
- **前置条件**：订单状态为"已确认"（未办理入住即可取消，宽松规则）
- **主流程**：在订单详情点击取消 → 二次确认 → 订单状态变为"已取消"，所占库存释放
- **异常**：已入住/已完成/已取消的订单不展示取消入口

### UC-06 前台查询订单

- **参与者**：前台
- **主流程**：前台登录后台 → 按订单号或住客手机号查询订单 → 查看订单详情
- **说明**：查询结果是办理入住的入口

### UC-07 办理入住

- **参与者**：前台
- **前置条件**：查到目标订单
- **主流程**：前台打开订单 → 系统校验入住条件（见 BR-06）→ 校验通过 → 前台登记住客身份证号 → 从该房型当前空闲房间中选择一间分配 → 确认 → 订单状态变为"已入住"
- **异常**：订单状态非"已确认"、当前日期不在可入住窗口内、身份证格式不合法、该房型无空闲房间 → 拒绝办理并提示具体原因

### UC-08 办理退房

- **参与者**：前台
- **前置条件**：订单状态为"已入住"
- **主流程**：前台在订单上点击退房 → 订单状态变为"已完成"，房间释放

### UC-09 房型与房间维护

- **参与者**：前台
- **主流程**：前台可新增/修改房型（名称、单价、介绍）与房间（房间号、所属房型）
- **约束**：修改/减少房间（含将房间改挂其他房型）后，该房型的房间总数不得小于当前有效订单数（已确认+已入住），否则拒绝并提示"该房型存在有效订单，请先处理相关订单"

## 5. 核心业务规则

### BR-01 预订规则

- 必须登录后才能创建预订；预订人 = 当前登录住客
- 一个订单 = 一个房型 × 一间房 × 连续多晚；晚数 = 离店日期 − 入住日期
- 入住日期不得早于提交当天；离店日期必须晚于入住日期
- 订单必填信息：住客姓名、手机号（需符合手机号格式）
- 允许代订：住客姓名、手机号可与登录账号不一致（代他人预订）；前台按手机号查订单时，查的是订单上的住客手机号
- 预订时不指定具体房间，具体房间在办理入住时才分配（见 BR-05）

### BR-02 防超卖

- 库存口径：库存 = 该房型物理房间总数，不允许超售，无房间停用态
- 计算方式：逐日计算。某房型某日的已占数量 = 当日处于"已确认"或"已入住"状态、且订单日期区间覆盖当日（覆盖入住日至离店日前一日）的订单数；每日已占数量不得超过该房型物理房间总数
- 某日期区间的剩余可订数量 = 区间内每日"（房间总数 − 当日已占数量）"的最小值
- 校验时机：查询可订状态时展示剩余数量；**提交预订时再次强校验**，并发下以提交校验为准，先到先得

### BR-03 订单金额

- 订单金额 = 房型单价 × 晚数，预订提交时计算并固化到订单上（之后房型调价不影响已生成订单）
- 支付方式：到店支付，系统不做在线扣款
- 单价允许小数（如 288.50 元）；晚到入住（入住窗口内、非入住日当天办理）不退差价，订单区间与金额不变

### BR-04 取消规则（宽松）

- 订单状态为"已确认"时，住客可随时取消（含入住日当天，只要尚未办理入住）
- 取消后订单状态变为"已取消"，释放所占库存
- 不支持改期；改期需求通过"取消后重新预订"满足

### BR-05 房间分配

- 预订阶段只管理房型的可订数量，不指定具体物理房间；具体房间仅在办理入住时分配
- 办理入住时，由前台从该房型当前空闲房间中选择一间分配
- 同一房间在同一时间只能分配给一笔"已入住"订单

### BR-06 入住校验（宽松窗口）

办理入住须同时满足：

1. 凭订单号或住客手机号可查到订单
2. 订单状态 = 已确认
3. 当前日期在可入住窗口内：**入住日当天 ≤ 当前日期 < 离店日期**
4. 登记住客身份证号，须符合 18 位身份证号格式

任一不满足则拒绝办理，并提示具体原因。

补充：超过入住窗口仍未办理入住的订单，系统不做自动处理，状态保持"已确认"，住客可自行取消（此为演示项目的已知简化，生产版应由定时任务自动关闭）。

### BR-07 退房规则

- 仅"已入住"状态的订单可办理退房
- 退房后订单状态变为"已完成"，房间立即释放
- 允许提前退房（离店日前退房）：剩余晚数不退差价；退房后剩余晚数立即可再售（"已完成"订单不计入有效订单，库存自动恢复）

### BR-08 订单号规则

- 订单号必须包含 `HR + 日期` 要素（如 `HR20261003-0001`），其中日期为下单日期，全局唯一，具体生成方式不限

## 6. 订单状态流转

### 6.1 状态定义

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| 已确认 | 预订成功，等待入住 | 否 |
| 已入住 | 前台已办理入住并分配房间 | 否 |
| 已完成 | 已退房离店 | 是 |
| 已取消 | 订单被住客取消 | 是 |

### 6.2 流转表

| 源状态 | 触发事件 | 操作人 | 目标状态 | 附带动作 |
| --- | --- | --- | --- | --- |
| —（创建） | 提交预订且库存校验通过 | 住客 | 已确认 | 生成订单号、固化金额、占用库存 |
| 已确认 | 取消订单 | 住客 | 已取消 | 释放库存 |
| 已确认 | 办理入住（校验通过） | 前台 | 已入住 | 登记身份证号、分配房间号 |
| 已入住 | 办理退房 | 前台 | 已完成 | 释放房间 |

说明：已取消、已完成均为终态，不允许任何后续操作；不存在"已入住 → 已取消"等逆向流转。

## 7. 验收标准

每条对应一个可验证场景，后续据此编写测试用例。

**账户与权限**

- AC-01：未登录用户可浏览房型列表；点击"预订"时被引导至登录页
- AC-02：使用未注册手机号可注册成功，注册后可登录；重复手机号注册被提示
- AC-03：住客"我的订单"中只能看到本人订单，看不到他人订单
- AC-04：住客访问前台功能被拒绝；预置 admin 可登录前台后台

**浏览与预订**

- AC-05：选择入住/离店日期后，各房型展示剩余可订数量；无剩余时展示"已订满"且无法提交
- AC-06：离店日期早于或等于入住日期时无法提交并提示
- AC-07：成功创建订单后：生成含 HR+日期的唯一订单号，状态为"已确认"，金额 = 单价 × 晚数，订单含姓名与手机号
- AC-08（防超卖）：某房型某日期区间仅剩 1 间时，两名住客同时提交预订，一笔成功、一笔失败并提示"已订满"，成功订单数不超过物理房间数

**取消**

- AC-09："已确认"订单取消成功：状态变"已取消"，该日期区间剩余可订数量 +1
- AC-10："已入住""已完成""已取消"订单无取消入口，通过其他途径提交取消也无效

**前台入住**

- AC-11：前台可按订单号、住客手机号查到订单
- AC-12：对状态=已确认、当前日期在 [入住日, 离店日) 内的订单，登记合法身份证号并选择空闲房间后办理成功：状态变"已入住"，订单上出现房间号与身份证号
- AC-13：当前日期早于入住日、或晚于等于离店日的订单，办理入住被拒绝并提示
- AC-14：状态非"已确认"（已入住/已完成/已取消）的订单，办理入住被拒绝并提示
- AC-15：身份证号不符合 18 位格式时，办理入住被拒绝并提示
- AC-16：办理入住时可分配的房间列表中，不含已分配给在住订单的房间；同一房间不能被两笔在住订单同时占用

**退房与终态**

- AC-17："已入住"订单退房成功：状态变"已完成"，该房间重新出现在可分配房间列表中
- AC-18：非"已入住"状态的订单无法办理退房
- AC-19："已完成""已取消"订单为终态：不可取消、不可入住、不可退房

**基础数据**

- AC-20：系统初始化后存在预置房型（3~4 种）、每个房型预置若干房间，以及预置 admin 账号，无需手工录入即可演示主链路
- AC-21：前台新增/修改房型与房间后，住客侧房型列表与可订数量同步变化

## 8. 非功能要求

### 8.1 可用性与演示要求

- 系统一键可启动、开箱可演示：预置房型、房间、admin 账号等基础数据
- 主链路（预订→查询→入住→退房）操作流程清晰，每步有明确结果反馈
- 关键业务提示（订满、不可取消、不满足入住条件）文案明确，便于演示讲解

### 8.2 基本质量要求

- 并发安全：预订提交在并发下不超卖（对应 AC-08）
- 数据安全：用户密码不明文存储；住客仅能访问本人订单
- 演示规模下（几十个用户、几百笔订单）页面操作响应无明显卡顿

### 8.3 本期省略项说明

按 skill 的标准需求模板，以下内容对本演示项目非必要，**明确省略、不在本期实现**：埋点与行为分析、运营报表、监控告警、审计日志、国际化、无障碍适配。如面试中被问及，口头说明"演示项目从简，生产版需补齐"即可。

## 附：需求口径确认记录

本文档基于 2026-10-03 需求澄清会议（14 项确认问题）输出，关键口径：角色仅住客+前台、防超卖为库存唯一硬规则、取消走宽松规则（未入住随时可取消）、入住校验走宽松窗口（入住日 ≤ 当天 < 离店日）、入住需登记身份证、订单号含 HR+日期、本期不做支付与改期。

v1.1 修订（2026-10-04 需求评审）：明确库存逐日计算口径与"库存=物理房间总数、不超售"（BR-02）；允许代订（BR-01）；晚到入住不退差价（BR-03）；超期未入住订单不做自动处理（BR-06 补充）；提前退房不退差价且剩余晚数可再售（BR-07）；订单号日期为下单日期（BR-08）；房间维护不得使房间数低于有效订单数（UC-09 约束）；预置数据补充房间（AC-20）；房间维修/停用列入本期不做（1.3）。
