## 3. 关键设计与取舍

### 3.1 防超卖：库存行预创建 + 原子条件更新

- **遇到的问题**：初版设计允许下单事务内"UPDATE 失败则 INSERT 库存行"。T7 并发集成测试实测出现两类死锁：① REPEATABLE READ 下对不存在的行做加锁 UPDATE 产生间隙锁，并发 INSERT 同一间隙互相等待成环；② INSERT 撞唯一索引后 InnoDB 为重复键检查持有 S 锁至事务结束，并发事务请求 X 锁形成 S→X 升级死锁（READ COMMITTED 同样存在）。
- **怎么解决**：把"库存行存在"变成数据不变式——启动时按 `INSERT IGNORE` 预创建 `[今天, 今天+730天)` 的库存行（`InventoryPreCreator.java:17`），下单热路径只剩对已存在行的条件更新 `UPDATE ... SET occupied_count = occupied_count + 1 WHERE ... AND occupied_count < total_count`（纯记录锁，原子）；超出窗口的日期由 `InventoryRowCreator.java:17` 以 REQUIRES_NEW 独立小事务懒建兜底，绝不把 INSERT 引入下单事务。日期区间按升序占用，固定加锁顺序。
- **为什么这样选**：条件更新在 MySQL 行锁下天然原子，不超卖；预创建后占用路径无死锁面，且不需要改隔离级别或引入分布式锁等更重方案。该思路来自测试暴露问题后的一次方案讨论，随后回写为技术方案 v1.2 决策 13（依据：docs/02 §5.1；`ai-process/编码任务清单.md` 关键偏差）。

### 3.2 订单号生成：序号行同样不能在下单事务内 INSERT

- **遇到的问题**：TC-G07（20 线程并发首单）实测 `INSERT INTO order_seq` 撞主键/间隙直接死锁，与库存行问题同源。
- **怎么解决**：与库存行同一解法——无锁一致性读判断 + `OrderSeqRowCreator.java:15`（REQUIRES_NEW 独立小事务 `INSERT IGNORE`）建行 + 条件更新 +1（`OrderNoGenerator.java:28`）。序号与订单同事务，序号不回滚复用。
- **为什么这样选**：语义等价于技术方案原本的"UPDATE 失败则 INSERT 重试"，但无死锁面；允许跳号换取"绝不阻塞下单事务"（BR-08 只要求全局唯一，docs/03 §11 已列为已知简化）。

### 3.3 房间并发分配：行锁串行化 + 独立事务复查 + 生成列唯一索引兜底

- **遇到的问题**：① 两个 admin 并发把同一房间分给两笔订单（TC-G04）；② 复查"房间是否有在住订单"时，REPEATABLE READ 下事务快照在首次读时建立，同事务普通 SELECT 读不到并发事务新写入的在住订单；③ 改用 `SELECT ... FOR UPDATE` 复查又对唯一索引的 NULL 值产生间隙锁，两并发事务互锁死锁（v1.4 实测）。
- **怎么解决**：三层防线——入住事务内先对房间行 `SELECT ... FOR UPDATE` 串行化；复查改由 `CheckedInRechecker.java:25` 的 REQUIRES_NEW 独立只读小事务执行，按生成列 `active_room_id` 命中唯一索引做普通一致性读（不加锁、无间隙锁问题）；最后的入住 UPDATE 带 `status='CONFIRMED'` 源状态条件。数据库层用生成列 `active_room_id = IF(status='CHECKED_IN', room_id, NULL)` 加唯一索引兜底（`schema.sql:59,63`，利用 MySQL 唯一索引允许多个 NULL 的特性），代码路径即使失守也写不进去。
- **为什么这样选**：每一步都针对一个实测失效场景；生成列把核心业务规则"同一房间最多一笔已入住订单"（BR-05）固化为 DB 约束，是最便宜的最后防线。

### 3.4 房间不加"状态"字段，空闲由在住订单推导

- **怎么解决**：`room` 表无状态字段，"空闲房间 = 全部房间 − 已入住订单占用的房间"（`RoomService.java:64` listAssignableRooms，docs/02 §4.2）。
- **为什么这样选**：房间状态与订单状态是同一事实的两种写法，冗余存储必然带来一致性问题（入住/退房/取消都要双写）；推导后 UC-09 房间维护也无需维护状态字段。唯一性由 3.3 的生成列约束保证，推导不会读到脏结果。

### 3.5 金额口径：接口传"分"，前端唯一换算出口

- **遇到的问题**：浮点金额在前后端传递容易引入精度误差；且换算代码散落各处难以收口（评审中发现 api 层、组件内都有换算痕迹）。
- **怎么解决**：DB 存 `DECIMAL(10,2)`、后端内部 BigDecimal（元）、前后端接口一律传"分"整数（DTO 序列化层换算）；前端全程持"分"，换算只允许出现在 `hotel-web/src/utils/money.js` 三个函数（`formatYuan` 渲染 / `yuanToFen` 提交 / `fenToYuan` 回填），并写入 AGENTS.md 硬规则。订单金额下单时固化为 BigDecimal（BR-03），后续调价不回溯（TC-B09/B10）。
- **为什么这样选**：整数"分"彻底消灭浮点问题；"唯一出口"让评审可以直接 grep 验证口径是否被违反。

### 3.6 状态流转：一律带源状态条件的 UPDATE

- **怎么解决**：取消/入住/退房全部用 `UPDATE ... WHERE status='源状态'`（取消另带 `user_id`），影响 0 行即提示"订单状态已变更，请刷新查看"，禁止"先查后改"（docs/02 §5.3）。
- **为什么这样选**：先查后改在并发下有 TOCTOU 缝隙；条件更新把"判状态"和"改状态"合并为一次原子操作。TC-G06（取消+入住并发）实测终态自洽：要么已取消要么已入住，不存在中间错乱（`AdminConcurrencyTest`）。

### 3.7 UC-09 维护路径的并发安全（v1.4 实测修订）

- **遇到的问题**：① 房型/房间维护事务与下单事务并发时出现 50s 级锁等待——维护事务对库存范围加锁 bleed 到相邻房型首行，把独立事务的 `INSERT IGNORE` 堵死；② 减容同步若直接 `UPDATE total`，可能与并发下单交叉导致超卖。
- **怎么解决**：批量补建行改前置独立小事务完成后再加锁；减容用带守卫的条件更新（`SET total_count = 新值 WHERE occupied_count <= 新值`），再对"total 未同步的行"做 `FOR UPDATE` 加锁当前读复查（普通 count 受外层事务早期 RR 读视图影响会漏行），有残留即回滚；正在入住中的房间禁止改挂（"该房间正在入住中，不可调整"，TC-F09）。
- **依据**：docs/02 §4.2 v1.4 修订说明；`RoomService.java:103/133/165` 三处同步点；TC-G08（减容维护×并发下单，恰一方成功）。

### 3.8 鉴权与数据隔离

- token 为 UUID 落 `auth_token` 表（7 天过期），请求走 `X-Token` 头，`AuthInterceptor.java:25` 解析后放入上下文；未登录 401、越角色 403。
- 住客订单数据一律按 token 中的 `user_id` 过滤，**禁止信任前端传的 userId**（`CreateOrderRequest` 注释明示不含 userId；TC-A06/H03）；admin 调住客下单接口返回 403"前台账号不可创建预订"（TC-A11）。
- 统一响应 `Result{code,message,data}`，业务错误抛 `BizException`，`GlobalExceptionHandler.java:21-57` 覆盖参数校验/类型不匹配/唯一键冲突等七类兜底，message 一律用原型文档文案。

## 4. 技术亮点

1. **数据库生成列唯一索引防双住**（`schema.sql:59,63`）：`active_room_id` 虚拟列仅在 `status='CHECKED_IN'` 时取 `room_id`，利用 MySQL 唯一索引允许多个 NULL 的特性，用一行 DDL 把 BR-05 固化为 DB 约束。验证：TC-G04 并发分房仅一笔成功（`AdminConcurrencyTest`）。
2. **无死锁面的并发占用路径**：库存行预创建把下单热路径收敛为"纯记录锁条件更新 + 固定加锁顺序"，两类实测死锁（间隙锁成环、S→X 升级）从机制上消除（docs/02 §5.1 v1.2 实测结论）。验证：`InventoryServiceTest` 10 线程并发占用成功数恰为房间数；`OrderConcurrencyTest` TC-G01 8 线程抢 3 间恰 3 笔成功且每日 occupied 恒等成功订单数。
3. **三处 REQUIRES_NEW 独立小事务**：`InventoryRowCreator`（库存行懒建）、`OrderSeqRowCreator`（序号行懒建）、`CheckedInRechecker`（在住复查）——每一处都对应一个实测的并发失效场景（事务内 INSERT 死锁 ×2、RR 快照读不到并发新写入 ×1），是有判据的解法而非模式套用。
4. **并发测试即交付证据**：66 个集成测试用例中 8 个并发用例（`OrderConcurrencyTest` 5 例 + `AdminConcurrencyTest` 3 例），全部直接断言数据库终态而非仅接口返回：TC-G01 防超卖、TC-G02 抢最后一间、TC-G03 取消与预订交叉、TC-G04 并发分房、TC-G05 并发入住同一订单、TC-G06 取消+入住交叉、TC-G07 20 线程订单号唯一、TC-G08 减容维护×并发下单。并发类连跑多轮稳定（验收记录见任务清单 T8/T9/T12）。
5. **下单幂等防重复提交**：前端每次进入预订确认页生成 `requestNo`（UUID），服务端先查重、唯一索引 `uk_order_request_no` 兜底，撞索引的事务回滚后改查首次订单返回（docs/02 §5.1；TC-B14）——双击/网络重试不会产生重复订单或重复占库存。
6. **金额"分"口径全链路可 grep 验证**：接口整数分、前端唯一换算出口 `money.js` 三函数，评审时直接全文检索确认无违规换算点（T11 评审修订记录）。
7. **一键启动与幂等初始化**：`start.sh` 环境检测→前端构建→产物托管→打包→起库→起应用全链路；`schema.sql` 全量 `CREATE TABLE IF NOT EXISTS`、`data.sql` 全量 `INSERT IGNORE`。验证：TC-F01（全新环境清数据卷后一键启动，预置 4 房型/10 房间/admin 开箱可用）、TC-F02（重启后预置数据不重复、业务数据不受影响）均实测通过。
8. **零依赖页面截图脚本**（`ai-process/scripts/page-screenshot.mjs`）：仅用 Node 内置 WebSocket/fetch 走 Chrome DevTools Protocol 驱动本机 Chrome，注入登录态后截取全部 13 页（`docs/screenshots/`），未引入 puppeteer 等新依赖。
